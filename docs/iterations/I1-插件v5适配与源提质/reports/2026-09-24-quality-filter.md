# 画质优先筛选记录（2026-09-24）

需求：75 寸电视，画质优先，宁可少而精，不要"能播但糊"的线路。

## 一、探测方法

工具：[`../scripts/probe-quality-fast.ps1`](../scripts/probe-quality-fast.ps1)（无外部进程）

| 线路类型 | 探测方式 | 成本 |
| --- | --- | --- |
| 多码率主列表（`#EXT-X-STREAM-INF`） | 直接取声明里最高的 `RESOLUTION` / `BANDWIDTH` | 1 次 GET |
| 单码率媒体列表 | 下载首个可用分片前 128 KB，解析 MPEG-TS 里 H.264 SPS（`pic_width_in_mbs` + frame crop）得到真实分辨率 | 1~3 次 GET |
| 加密 / fMP4 | 无法解析 SPS，标记未知 | — |

为什么不用 ffprobe：每条线路都要新建一个 runspace + 启动一个外部进程（Windows 下进程创建约 100ms），
且 ffprobe 默认会拉整条直播流探测，单条 3~6 秒。改为 .NET 内并发 + 自解析 SPS 后，246 条 **53 秒**跑完。

注意：ffprobe 直接探测 master playlist 会**选到最低档**（实测 `cdrmldcctv1_1` 报 640x360，而该主列表实际含
1920x1080/3.2Mbps 档），所以画质判定不能依赖它的选档结果。

## 二、全量结果（246 条聚合线路）

```
ts-sps    17   实测到真实分辨率
master     1   主列表声明画质
probe-failed 171  播放列表可拿，但分片 404 / 超时
unreachable  57   连播放列表都取不到
```

画质分布（能测到的 18 条）：`2160p × 1`、`1080p × 10`、`720p × 6`、`540p × 1`。

**关键结论**：原第三节"246 条可用线路"只校验了 `#EXTM3U`，实际**能验证到视频流的只有 18 条（7%）**。
这也解释了第四节设备侧抽样为何大量 NOFRAME。

## 三、筛选规则

沿用了 `my-tvForTest` 的既有过滤逻辑（`TVList.kt`），避免两边标准不一致：

| # | 规则 | 来源 |
| --- | --- | --- |
| 1 | **剔除**黑名单域名（含所有子域）：`iill.top` | `TVList.BLOCKED_HOSTS` |
| 2 | **剔除**疑似录像轮播：`kwimgs`（快手 CDN）、`/video-hls/`（点播转直播） | `TVList.isLoopSuspect` |
| 3 | **剔除**点播文件：`.mp4` / `.mkv` / `.avi` | `TVList.isVodUrl` |
| 4 | **剔除**假源与临时授权：`raw.githubusercontent.com`（内容为 YouTube 播放列表）、`auth=` / `testpub` | 本次实测 |
| 5 | **剔除**实测分辨率 < 720p | 本次新增（75 寸画质优先） |
| 6 | **剔除**未验证到视频流的线路（`probe-failed` / `unreachable`） | 本次新增 |
| 7 | **排序**：`画质档(≥1080p → ≥720p) → 线路类别(https 非裸 IP → http 域名 → 裸 IP) → 延迟` | 本次新增 |

规则 1~3 实际命中的是两条**快手轮播**线路（东方卫视、湖南卫视的 `txmov2.a.kwimgs.com`）：
分辨率看着是 720p，内容是循环短视频而非直播，属于必须剔除的"假直播"。
4. 原有内置条目（`webview://` 央视频页面 + 官方 CDN）**位置不变，仍在前**

保留未验证线路可用 `-KeepUnverified` 开关（默认关闭）。

## 六、待跟进

- 播放器输出分辨率档位 `resolutionMode` 默认 `high`；若电视支持 4K，可在设置中确认（河北卫视有 4K 源）。
- `webViewResolution` 默认 **720P**，75 寸下建议改为 1080P/2K（影响 `webview://` 频道的页面渲染尺寸）。
- 未验证线路只是"宿主侧验不到"，设备侧可能能播（CCTV-4 六条全部 `probe-failed`，但设备实测有 3 条可用），
  后续若要做 fallback 池，需要用设备侧口径重新评估，不能直接沿用宿主结论。
