## 一、巡检脚本

一条命令产出 JSON 明细 + Markdown 报告：

```powershell
pwsh -File scripts/check-sources.ps1                                    # 巡检内置源
pwsh -File scripts/check-sources.ps1 -Playlist cctv-filtered.m3u        # 任意 m3u
pwsh -File scripts/check-sources.ps1 -Baseline reports/check-xxx.json   # 跨期对比
```

报告含：总览（可用率 / 画质达标率 / 延迟分位）、画质分布、状态分布、域名集中度、
需关注项（无可用线路的频道 / 直连全失败 / 低于 720p / 黑名单命中）。

无外部进程，全部在 .NET 内并发完成；`webview://` 条目单独统计（站点页面解析，宿主侧无法直连探测）。
文件名带输入标识（`check-<输入名>-<日期>`），避免同一天巡检不同 playlist 互相覆盖。

### 关键教训：并发参数

| 配置 | 直连可用率 | 耗时 |
| --- | --- | --- |
| 并发 32 + 超时 4s | **20%（7/35）** | 12.4 s |
| 并发 8 + 超时 15s | **100%（35/35）** | 4.1 s |

探测是「阻塞式等待 HTTP」（sync-over-async），并发过高会互相拖慢并集体撞上超时窗口——
表现为**并发越高、越慢、误判越多**。默认已改为并发 8 / 超时 15s，并把该教训写进脚本头部注释。

同一个坑也影响过历史结论：`probe-quality-fast.ps1`（已被本脚本取代）用的是并发 32 + 超时 4s。

## 四、补源评估：结论是不补

候选池就是上述 21 条 ≥720p 可用线路，逐条比对当前 39 个纯 `webview://` 频道：

| 候选 | 目标频道 | 是否可补 | 原因 |
| --- | --- | --- | --- |
| 江西卫视 1080p `112.27.5.218:9901/tsfile/...` | 江西卫视 | 技术上可 | 裸 IP 的 IPTV 内网源，跨网络环境易失效 |
| 福建海峡卫视 1080p `38.64.72.148/hls/...` | 福建东南卫视 | 存疑 | 裸 IP；且频道名与实际信号未必对应 |
| 湖南卫视 720p `kwimgs.com` | 湖南卫视 | 否 | 命中黑名单（快手录像轮播） |
| 河南卫视 576p / 黑龙江卫视 64p | 同名频道 | 否 | 低于 720p 画质门槛 |

**不建议执行补源**，理由：

1. 收益极小：真正可补的只有 1~2 条，且都是裸 IP 的 IPTV 源。
2. 风险明确：裸 IP 源跨网络环境（电信/联通/移动）失效概率高，会把「稳定可用的单线路频道」
   变成「首个线路随机失败」——反而制造出需要回退的场景。
3. 现状已达标：39 个纯 `webview://` 频道实测 8/8 起帧、全部 1080p、首帧约 2 s，
   画质与稳定性均优于可补的候选源。
4. 与迭代原则冲突：本迭代明确「画质优先、宁可少而精」，为凑覆盖率引入低质量源是反向操作。

若将来要提升兜底覆盖率，正确路径是**找官方源**（`cztv.com` / `bestv.cn` / `hebtv.com` / `nmtv.cn`
这类省级台官方 CDN），而不是放宽聚合源门槛。本次 21 条可用线路里官方域名的只有 8 条，且都已在用。

## 五、复用检查点

- 巡检报「无可用线路频道」→ 先用 `device-sample-test.ps1` 做设备侧确认再决定剔除
  （宿主判失败 ≠ 设备不可用，已多次出现）。
- 巡检报「低于 720p」→ 画质优先场景直接剔除，无需复验。
- 巡检报「黑名单命中」→ 直接剔除，并把新域名补进脚本黑名单。
- 跨期用 `-Baseline` 对比，重点看「新失效」列表。
